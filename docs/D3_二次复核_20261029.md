## 3. 仍需修复的问题

### 3.1 固定研究日没有约束新评价工具（必须修复）

位置：`app/agent/tools.py:299`、`app/factor_research/service.py:27`、`app/agent/tools.py:303`。

模型给出的结束日期仍直接传给服务；服务用这个日期设置查询截止日，没有接收或核对会话的可信研究日。报告读取也没有核对可信截止日。限制普通行情工具不能保护另一条新工具路径。

复现仍是研究日 2025-05-30，请求截至 2025-06-04，任务完成并保存 76 条研究日之后的非空标签。因此“每日排序不读信号日之后的数据”只修复了排序输入，不能证明整次研究没有使用未来信息。

修复要求：提交、读取、比较共同使用服务端可信截止日；信号日、标签结束日、股票池、输入版本均须满足会话约束。不能只在页面设置最大日期，也不能让模型自己声称日期合法。新增检查须要求越界任务不产生结果，读取既存未来任务也被拒绝。

### 3.2 修改本金仍误用旧回测（必须修复）

位置：`app/backtest/factor.py:77`。

默认请求摘要遗漏初始本金和股票池。第一次完成后，换本金再次请求直接返回旧编号，没有重新计算。本轮两个请求分别是 100000 与 200000，编号均为 27。

修复要求：完整规范化所有影响结果的输入，包括本金、股票池、日期、固定版本、引擎版本和输入数据版本。同一请求标识对应不同内容时应拒绝，不能静默取旧记录。还应明确旧引擎已算出的结果如何失效，避免重启后继续命中修复前的错误结果。

### 3.3 取消能被计算完成覆盖（必须修复）

位置：`app/factor_research/service.py:141`、`app/factor_research/service.py:173`、`app/factor_research/service.py:336`。

工作线程只在每个信号日开始检查取消。最后一步计算结束后，无条件写入并把任务改为 COMPLETED。在计算最后阶段取消，取消操作虽然成功，随后仍会被覆盖。

独立检查仅在探测进程内给最后一次分组计算加同步屏障，没有改应用文件：暂停最后一步 → 调用真实取消接口 → 确认 CANCELLED → 放行原计算与原写库。最终实际状态为 COMPLETED，保存 38 条结果。

修复要求：结果发布与状态转换必须在同一数据库事务内核对并锁定任务；取消已成功就不能再发布为完成。重复启动、退出登录、进程中断和回测最终发布也需要同样的并发约束。仅增加一次提交前状态查询仍可能存在竞争。

## 4. 其他交付缺口和本轮边界

- 新回测仍是独立成交路径，没有接入原 C 的撮合与现金账本。代码没有原 C 的涨跌停、上市前五日、退市和跨除权事件等完整限制；更换个人费用不能成为省略这些限制的理由。本轮没有构造这些事件的新成交样例，属于代码检查发现的剩余缺口。
- 回测增加了策略/费用摘要，但评价 snapshot 仍只是参数摘要，没有冻结真实输入数据，也没有数据变更后重放的一致性证明。
- 后台评价仍可对同一 RUNNING 请求再次启动线程；回测写入前的状态检查没有锁定状态。崩溃恢复也不能只靠正常退出时的处理。
- 公共公式已加入研究/策略的页面选择；前百分比在服务里已支持，但策略页面仍只提供持有只数。
- 分组表和平均秩相关结果已在新进程页面实际显示；本轮通过一个公共公式的完整评价读取流程，不表述成全部公式和分组边界均已验收。
- 实现方已说明真实 DeepSeek 没有在修复后重跑，小样本回答的比例引用问题仍在。它不是等外部数据才能修复的问题，不能列为已通过。
- 本轮没有重验外部财报导入、备份恢复与全部换用户流程。上一轮记录只作为历史证据保留。
