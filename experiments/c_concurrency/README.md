# E5：并发超卖实验

在独立样本库上运行：

```powershell
.venv\Scripts\python.exe experiments/c_concurrency/run.py
```

分别执行两类场景，每组 50 个连接：`stock_sell` 争抢同一份 100 股持仓，每单卖出 100 股；`cash_freeze` 争抢同一笔 10,000 元可用资金，每单冻结 10,000 元。用屏障让不加锁组全部先读到初始可用值，再扣减，稳定复现超卖与超额冻结；另外三组分别使用 `SELECT FOR UPDATE`、带余额条件的原子 `UPDATE`、`SERIALIZABLE` 加失败重试。

`results.csv / results.json / results.md` 保存实测吞吐量、接受和拒绝数量、剩余可用资源、总预留资源和序列化重试次数。正常结果是接受 1 笔、拒绝 49 笔，剩余可用资源为 0。不加锁组最终为 -4,900 股，或在 10,000 元余额上冻结 500,000 元。拒单是正常业务结果，不算数据库正确性错误。未加锁组故意允许负数，用来显示缺乏保护的后果，不使用生产持仓或账户表。

资金场景以固定预留金额演示竞争，不计算费用；真实下单函数的费用、冻结和现金对账由应用账号集成测试覆盖。

计时从所有连接就绪后开始，不包括建立连接；每组运行一次，是本机教学实验，不能作为普遍性能排名。串行化策略遇到 SQLSTATE 40001 时重试整个事务，最多 100 次。表名每轮随机生成，结束只删除本轮表。

真实交易接口另由 `tests/c/test_services.py::test_50_concurrent_buy_and_sell` 验证：50 个真实 `app_user` 请求调用 C 的下单函数，检查冻结上限、持仓上限、撤单释放与资金对账。
